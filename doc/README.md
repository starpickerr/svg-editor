# SVG 编辑器——设计与实现报告

Git 仓库：[starpickerr/svg-editor](https://github.com/starpickerr/svg-editor)

## 一、架构方案

### 1. 模块划分

项目使用 TypeScript 开发，采用模块化设计，将图形模型、编辑操作、文件处理和命令行交互分离。

| 模块          | 职责                                   |
| ------------- | -------------------------------------- |
| `model/`    | 图形对象、几何操作、容器层级和文档管理 |
| `commands/` | 编辑命令的执行、撤销与重做             |
| `svg/`      | SVG 文件的解析、序列化和读写           |
| `cli/`      | 命令解析、分发及终端输出               |
| `main.ts`   | 程序入口                               |

![模块架构图](architecture.svg)

### 2. 设计模式的选择

**Command（命令模式）**

使用 `EditCommand` 封装创建、删除、移动、缩放等编辑操作，由 `Editor` 统一管理执行、撤销和重做。

每条命令对应一个撤销单元。通过编辑前后的文档快照实现历史恢复，并在文档副本上执行修改，确保失败操作不会破坏原有状态。

**Composite（组合模式）**

使用抽象类 `Shape` 定义图形的统一操作接口，由 `Group` 管理子图形。

普通图形和容器均支持移动、缩放等操作。操作容器时递归处理其子元素，避免针对每种图形重复编写逻辑。

此外，通过 `ShapeFactory` 集中管理图形创建，便于后续扩展类型。

本阶段仅保留两处按名字分派：`CommandRouter` 将命令名映射到处理实现，`ShapeFactory` 将图形类型名映射到类。两处均为**待重构点**，后续插件化阶段再改为开放注册；当前不实现 `box` 或插件系统。移动、缩放、属性修改、复制、树显示和 SVG 序列化通过对象接口协作，不额外按图形标签分派行为。

### 3. 依赖方向规则

模块遵循单向依赖原则：

- `model` 不依赖其他业务模块。
- `commands` 依赖 `model`。
- `svg` 依赖 `model`，并使用 XML 库及文件系统接口。
- `cli` 可以调用上述模块，但底层模块不能反向依赖 `cli`。
- `main.ts` 负责启动程序，不包含具体业务逻辑。

这样能够使领域模型独立于命令行和文件系统，降低模块间的耦合。

### 4. 变化点假设

| 可能的变化    | 设计考虑                                    |
| ------------- | ------------------------------------------- |
| 增加图形类型  | 通过 `Shape` 子类和 `ShapeFactory` 扩展 |
| 增加编辑命令  | 通过新增 `EditCommand` 子类实现           |
| 增加图形界面  | 保持模型与 CLI 分离，便于复用               |
| 扩展 SVG 支持 | 将解析和序列化集中在 `svg` 模块           |

### 2. 关键问题与修订

**分组操作的层级问题**

在设计 `group` 命令时，发现跨容器分组的父节点和图形顺序没有明确规定。

最终采用最近公共祖先确定新容器位置，并按照原文档的树形顺序排列成员，避免意外改变图形顺序。

**撤销重做的原子性问题**

最初的命令设计需要进一步考虑执行中途失败的情况。

因此采用文档副本执行编辑，仅在操作全部成功后更新当前文档，确保失败不会留下部分修改。

**SVG 导入的 ID 冲突问题**

外部 SVG 可能存在缺少 ID 的图形，直接按顺序自动生成名称可能与已有 ID 冲突。

最终改为先收集全部已有 ID，再为缺失 ID 的元素分配唯一名称。

这些问题在 AI 辅助实现和代码审查过程中得到识别与修正，并通过对应测试验证。

最终核验时保留了已有报告改写，补齐其中遗漏的两处名字分派待重构说明，并以本次实际执行结果更新验收记录。

### 3. 已采用的行为约定

- 同父级分组在最早被选节点的位置建组；跨父级分组在最近公共祖先下建组；组内保持原文档树的先序，与命令参数顺序无关。保留未选节点及空原父容器。
- 按任务明确的错误约定，禁止解散 SVG 的直接子容器。`front` 将元素移到同级最后绘制的位置，`back` 移到最先绘制的位置。
- 成功的 `init`、`read`、`save` 和 `canvas` 尺寸修改清空历史并建立屏障；下一条成功编辑解除屏障。失败命令保留文档、撤销重做栈及屏障。
- 无参数 `save` 使用最近一次成功 `read` 的路径，显式保存到其他路径不改变读入路径；`init` 清除该路径。
- SVG 读取保留额外属性，例如 `transform` 和 `font-size`；几何编辑使用元素局部坐标，不归一化任意变换矩阵。遇到不支持的元素或无效 XML 时整次读取失败，警告仅在整次读取成功后输出。

## 三、一致性自查

### 1. 模块划分

实际代码按照 `model`、`commands`、`svg` 和 `cli` 四个模块组织，与架构方案一致。

图形操作集中在 `model`，历史管理集中在 `commands`，文件处理由 `svg` 负责，CLI 主要完成交互与协调。

### 2. 依赖方向

通过检查源码中的实际引用关系：

- `EditCommand` 依赖 `SvgDocument`。
- `SvgCodec` 依赖领域模型及图形工厂。
- `CommandRouter` 调用 `Editor` 和 `SvgFileStore`。
- `model` 不依赖 CLI 或文件系统。

最终核验检查了全部 29 个生产类文件的相对导入与类名，符合上述模块依赖规则及一类一文件、文件名与类名一致的要求。未发现当前阶段的依赖方向违规或未记录的模块划分偏差。
